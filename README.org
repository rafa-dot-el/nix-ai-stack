#+title: nix-ai-stack: AI agents, MCP servers and tools for NixOS and Home Manager
#+author: Rafael
#+language: en

* Overview

One Nix flake for an AI workstation. Everything is built from source or pinned
by hash, and every wrapper ships with self-update and telemetry switched off
(ADR-0002).

It separates two things on purpose:

1. *Install and run from the CLI*: agents and tools you start yourself
   (=claude=, =hermes=, =slack=, =openspec=, ...). Enabled with
   =rafa.ai.agents.<x>.enable= and =rafa.ai.tools.<x>.enable=. No unit is ever
   created by these.
2. *Services*: things that run in the background as systemd units. MCP servers
   (=rafa.ai.tools.<x>.server.enable=), the =mcp= proxy, ollama and the Hermes
   dashboard. Always opt-in.

Both module systems expose the same tree, =rafa.ai= (ADR-0006). The packages
are also available as =packages.<system>.*= and through =overlays.default=
(=pkgs.rafa.ai.<name>=).

** Agents

| Package | What | Switch |
|---|---|---|
| =default= (=hermesFull=) | Hermes with Chromium, Piper TTS, browser-use, LSP servers, faster-whisper, sherpa wake word, dashboard and desktop | =agents.hermes.enable= |
| =hermes-slim= | Hermes CLI and TUI only | =agents.hermes.package= |
| =hermes-desktop=, =-x11=, =-wayland= | the Electron app; =hermes-desktop= picks the variant at runtime | with Hermes |
| =claude-code=, =claude-agent-acp= | Claude Code and its ACP adapter | =agents.claude.enable= |
| =claude-desktop=, =claude-desktop-fhs= | Claude Desktop; the FHS variant runs npx/uvx/docker MCP servers | =agents.claude.desktop.fhs= |
| =claude-usage= | Claude plan usage: CLI, polybar format, Prometheus exporter | =agents.claude.usage= |
| =goose-cli=, =goose-desktop= | goose; telemetry forced off, desktop updater patched off | =agents.goose.enable= (cli + desktop) |

Each agent has one root switch that turns on its default stack (for example
=agents.claude.enable= installs code, acp, desktop and usage); every part can
be turned off on its own. A root switch never starts a service.

* Services

Services are separate from installs. Nothing here starts unless you enable it.

** MCP servers (Home Manager, systemd user units)

=tools.<x>.server.enable= runs the tool as an MCP server and installs its CLI
too. Each enabled server is its own socket unit plus service, with its own
journal identifier, started on the first connection:

#+begin_src nix :eval no
{
  rafa.ai = {
    tools.slack = {
      server = {
        enable = true;                                  # mcp-slack.socket + mcp-slack.service
        listen.socket = "%t/rafa/mcp/servers/slack.sock";   # the default
        credentials.token = "/run/agenix/slack-token";  # LoadCredential, never the store
        environment = { };
        include = [ "search_*" "history" ];             # server-side filter (also exclude, rename, describe)
        timeout = 60;
      };
    };
    tools.gworkspace = {
      settings.auth.refresh_token.command = [ "pass" "show" "google/refresh-token" ];
      servers.gtasks.enable = true;                     # one entry per CLI: gdocs, gsheets, gcal, ...
    };
    tools.playwright.server.enable = true;
  };
}
#+end_src

Per-server options (the same for every tool): =enable=, =listen.socket=,
=environment=, =credentials=, =prefix=, =timeout=, =include=, =exclude=,
=rename=, =describe=, =restartSec=, =extraServiceConfig=.

- *Native* servers (Slack, gworkspace, tmpmail) receive the activated socket
  from systemd. *Stdio* servers (playwright, patternfly, calibre, zotero) run
  behind =mcp sidecar=, which makes them socket-activated too.
- =listen.socket= defaults to the pool directory
  =%t/rafa/mcp/servers/<name>.sock=. The proxy discovers servers by watching
  that directory. A socket elsewhere is not discovered by the proxy; register
  it with =mcp config add-mcp NAME --unix PATH= or connect to it directly.
- Servers do not need the proxy. Without =mcp.enable= they have their own
  units and nothing else.
- Your own binary: =mcp.servers.<name> = { enable; exec = [ ... ]; native; }=.

*** The proxy and profiles

#+begin_src nix :eval no
{
  rafa.ai.mcp = {
    enable = true;      # the mcp binary, mcp-proxy.service, rafa-mcp.target
    profiles.coding.servers = {
      playwright.include = [ "browser_*" ];
      gtasks.include = [ "list_*" "get_task" ];
    };
  };
}
#+end_src

Point an agent at a profile with =mcp client --profile coding= as its stdio MCP
command.

#+begin_example
agent --stdio--> mcp client --profile P --unix--> mcp proxy --unix--> %t/rafa/mcp/servers/<name>.sock
                                                                       (mcp-<name>.socket activates mcp-<name>.service)
#+end_example

- Filters run on both sides: =include=, =exclude= (exclude wins), =rename=,
  =describe=, matched on the original tool name. Two tools with the same
  exposed name are an error, never resolved silently.
- Config: Home Manager writes =~/.config/rafa/mcp.d/10-nix.yaml=; your own
  =~/.config/rafa/mcp.yaml= is edited with =mcp config ...= or
  =mcp config-tui=. A project's =.rafa/mcp.yaml= loads only with =--project=.
- =mcp doctor= checks the config, the health of the proxy and every server,
  and the token savings of each profile. The full reference is
  =src/mcp/README.org=.

** Hermes dashboard and gateway (NixOS)

=rafa.ai.agents.hermes.server= runs the web dashboard (=hermes dashboard=)
and/or the messaging gateway (=hermes gateway=) as separate systemd services.
They coordinate only through the shared =hermesHome=. The old
=services.hermes-agent= option path still works as an alias.

Shared options (=package=, =user=, =group=, =stateDir=, =hermesHome=, the
=lsp=, =voice=, =browser= and =gateway= toggles) sit directly under
=rafa.ai.agents.hermes.server.*=; dashboard-specific ones under
=rafa.ai.agents.hermes.server.dashboard.*=. =package= defaults to a build with
exactly the enabled features, and never includes the Electron desktop app.

#+begin_src nix :eval no
{
  rafa.ai.agents.hermes.server = {
    # Persistent application state (config.yaml, sessions, memory, cron),
    # shared by dashboard and gateway. Defaults to "${stateDir}/.hermes".
    hermesHome = "/var/lib/hermes-agent/.hermes";

    # Feature toggles for `package`; each defaults to true.
    lsp.enable = true;
    voice.enable = true;
    browser.enable = true;

    gateway = {
      enable = true;  # also controls whether messaging/matrix extras are in `package`
      extraArgs = [ ];
    };

    dashboard = {
      enable = true;
      bindAddress = "0.0.0.0";  # only applies when `domain` is unset
      port = 8080;              # 443 when `domain` is set; only nginx binds a privileged port
      openFirewall = true;

      # Optional: Let's Encrypt TLS through an nginx reverse proxy.
      domain = "hermes.example.com";

      # Optional: HTTP Basic Auth in front of it (requires `domain`).
      basicAuth = {
        enable = true;
        passwordFile = "/run/secrets/hermes-dashboard-htpasswd"; # never a Nix store path
      };

      # Optional: client-certificate verification (requires `domain`).
      # caFile is a public CA certificate, so a store path is fine.
      mTLS = {
        enable = true;
        caFile = ./my-client-ca.pem;
      };
    };
  };

  # Required whenever a vhost has enableACME; accepting the subscriber
  # agreement is your decision, so it is not set for you.
  security.acme.acceptTerms = true;
  security.acme.defaults.email = "you@example.com";
}
#+end_src

Without =domain=, the dashboard binds on =bindAddress=:=port= with no TLS: fine
for a VPN-only host, not for the open internet. With =domain= set, the
dashboard is forced to =127.0.0.1=, so the TLS and auth front door cannot be
bypassed from the local network.

PAM-based auth was left out: it needs a custom nginx build and gives the nginx
worker access to a PAM stack, a larger attack surface than basicAuth or mTLS.

* Configuration and tweaks

** Per-tool settings

Each tool's =settings= is rendered to its own file. They hold secret
/references/ only, resolved by the tool at start-up (={ command = [...]; }= or
={ file = ...; }=); a secret is never written to the Nix store or a unit file.
The CLI and the MCP server of one tool read the same file.

| Option | File |
|---|---|
| =tools.slack.settings= | =~/.config/rafa/slack.yaml= |
| =tools.gworkspace.settings= | =~/.config/rafa/gworkspace.yaml= |
| =tools.calibre.settings= | =~/.config/rafa/calibrectl.yaml= |
| =tools.zotero.settings= | =~/.config/rafa/zoteroctl/config.toml= |
| =voice= | =~/.config/rafa/voice.yaml=, plus stable links under =~/.local/share/rafa/voice/{tts,stt}= |
| =mcp= | =~/.config/rafa/mcp.d/10-nix.yaml= (yours: =~/.config/rafa/mcp.yaml=) |

** Voice

One Piper voice and one Whisper model for the whole stack:

#+begin_src nix :eval no
{
  rafa.ai.voice = {
    enable = true;                                  # default
    tts.voice = "en_GB-alba-medium";
    stt.language = "pl";                            # optional
  };
}
#+end_src

Hermes and Slack read =voice.yaml=. Hermes's wake word is configured in
=config.yaml=; the default supports any English phrase without training:

#+begin_src yaml :eval no
wake_word:
  provider: sherpa
#+end_src

** Hardening (no self-update, no telemetry)

Every wrapper defaults the variables in =lib/hardening.nix= with
=--set-default=, so any of them can still be overridden. They cover each
tool's self-update and telemetry switches; the policy is ADR-0002.
=checks.hardening= verifies that every wrapper sets each variable, sets none of
the forbidden ones, and that =hermes --version= makes no off-host =connect()=.

=rafa.ai.hardening.enable= (default true) also installs the config-only part for
Hermes as =~/.local/share/rafa/hermes/hardened-config.yaml=, to merge into a
profile:

#+begin_src yaml :eval no
updates: {check: false}
plugins: {auto_update_check_hours: 0}
model_catalog: {enabled: false}
security: {allow_lazy_installs: false}
lsp: {install_strategy: manual}
telemetry: {shared_metrics: {enabled: false}}
#+end_src

What cannot be switched off (verified against the source):
- Hermes fetches =models.dev/api.json= for model metadata; only its URL is configurable.
- =browser-harness --doctor= and =--update= contact PyPI when run explicitly.

** Hermes browser automation

The CLI has two browser backends:
- *browser-use*: agent-driven browser control (=browser_exec=, the default
  backend; the =browser-use= CLI is always on PATH in this package).
- *agent-browser*: Hermes's built-in CDP-driven browser toolset.

Hermes starts its own Chromium on demand: the first =browser_exec= call of a
session launches the packaged, headless Chromium through =agent-browser=
(upstream's =_resolve_managed_chromium_cdp=). Nothing runs beforehand, and
nothing starts at =hermes= startup.

A CDP endpoint set by the operator (=BROWSER_CDP_URL=, =BU_CDP_URL=,
=BU_CDP_WS=, or =browser.cdp_url= in config.yaml) takes precedence and is used
as-is; Hermes launches nothing in that case.

* Container image

=rafadotel/ai= on Docker Hub is the full Hermes build as an OCI image, built
with =pkgs.dockerTools.buildLayeredImage= (no Dockerfile). It is =linux/amd64=
only; =arm64= is not in CI yet (=task oci:push= publishes one from an aarch64
host).

#+begin_src bash :eval no
podman pull docker.io/rafadotel/ai:latest
podman run --rm -it docker.io/rafadotel/ai:latest
#+end_src

Tags: =latest= (tracks =main=) and one per release, named like the git tag
without its leading "v" (git tag =v2026.11.11= is image tag =2026.11.11=).

* Building from source

#+begin_src bash :eval no
nix build github:rafa-dot-el/nix-ai-stack#default --no-link       # hermesFull
nix build github:rafa-dot-el/nix-ai-stack#hermes-slim --no-link   # CLI and TUI only
nix build github:rafa-dot-el/nix-ai-stack#claude-code --no-link   # any package by name
#+end_src

With this repo checked out, use Task: =task build=, =task build:slim=,
=task build:desktop=, =task oci:build=, =task oci:push=, =task cache:push=,
=task tag=, =task release=.

Supported systems: x86_64-linux and aarch64-linux. To build for aarch64 from
x86_64 you need a remote builder or binfmt emulation.

* Troubleshooting

** An MCP server does not answer

#+begin_src bash :eval no
mcp doctor
systemctl --user status mcp-proxy mcp-<name>.socket mcp-<name>.service
journalctl --user -u mcp-<name> -n 50
#+end_src

A server starts on its first connection, so an inactive =.service= with an
active =.socket= is normal.

** Piper TTS not found

#+begin_src bash :eval no
ls -la ~/.local/share/rafa/voice/tts ~/.local/share/rafa/voice/stt
cat ~/.config/rafa/voice.yaml
#+end_src

** Hermes browser automation not working

Check the agent log for the session that =browser_exec= creates:

#+begin_src bash :eval no
grep -E "Created local browser session|browser_exec" "${HERMES_HOME:-$HOME/.hermes}/logs/agent.log" | tail -5
#+end_src

If the session never starts, the =browser_exec= result carries the failure from
browser-harness or agent-browser in its =stderr=. If a CDP endpoint is
configured (see [[*Hermes browser automation][Hermes browser automation]]), check that it is reachable.

** Hermes LSP server not detected

Verify the server is on PATH, and set =lsp.install_strategy: manual= in
config.yaml:

#+begin_src bash :eval no
which pyright typescript-language-server gopls rust-analyzer clangd nixd
#+end_src

** Build timeout or OOM

A local build without the binary cache takes about 30 minutes and 8 GB of RAM.
Use the cache or give the machine more resources.

* Development

| Task | Runs |
|---|---|
| =task check= | lint and flake evaluation |
| =task check:inputs= | every nixpkgs in =flake.lock= follows a root channel |
| =task test= | every flake check, VM tests included |
| =task test:check -- <name>...= | only the named flake checks |
| =task rust:test=, =task rust:cov= | the Rust workspace; coverage gate 95% pure, 85% overall |
| =task py:test= | calibrectl and zoteroctl, coverage gate 95% |
| =task test:unit=, =task test:integration= | Hermes gates and the ACP integration tests against a scripted fake OpenAI backend (=-- -m "not network"= for the offline subset) |
| =task check-update= | pinned vs latest version of Hermes and every package (exit 0: an update is available) |
| =task update= | bump Hermes (=task hermes:update=) and every package (=task update:packages=), building and testing each |

Architecture decisions are in =gov/adr/=; requirements in
=gov/requirements.org=. The Hermes integration tests give each test its own
profile, HOME, TMPDIR and browser runtime dirs under =/tmp/hi-*=; set
=HERMES_IT_KEEP_SESSIONS=1= to keep them after a run.
